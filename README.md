# Persian Store V2 — فروشگاه اینستاگرامی با ربات تلگرام

استقرار: `node scripts/setup.mjs` (مهاجرت‌ها خودکار اعمال می‌شوند، شامل 0010) و سپس deploy ورکر.

## کلیدهای Runtime (بخش Variables and Secrets پنل Cloudflare)

دو کلید `MINIAPP_ENABLED` و `USERS_ENABLED` **اختیاری** هستند و از قبل
در `wrangler.json` (بخش `vars`) ثبت می‌شوند؛ بنابراین در داشبورد هم
در مسیر Workers → Settings → Variables قابل مشاهده‌اند. اگر ورکر قدیمی
دارید و این دو را در داشبورد نمی‌بینید، همان دو خط را به `wrangler.json`
اضافه کنید و دوباره deploy بگیرید:

```json
"vars": { "MINIAPP_ENABLED": "on", "USERS_ENABLED": "on" }
```

| متغیر | پیش‌فرض | توضیح |
|---|---|---|
| `MINIAPP_ENABLED` | **on** | با `off` / `0` / `false` مینی‌اپ مدیریت خاموش می‌شود |
| `USERS_ENABLED` | **on** | با `off` / `0` / `false` ثبت‌نام/ورود مشتریان و `/account` خاموش می‌شود |
| `BOT_TOKEN`, `BOT_WEBHOOK_SECRET`, `TURNSTILE_SECRET_KEY` | — | Secrets (همان مقادیر قبلی) |

مقادیر مجاز برای فلگ‌ها: `true/false/1/0/on/off/yes/no` (حروف بزرگ/کوچک فرق ندارد). حذف متغیر = فعال.

## آپلود تصویر (لوگو، بنر اسلایدر، عکس محصولات و دسته‌ها)

دو روش پذیرفته می‌شود (حداکثر ۴ مگابایت):

1. **عکس تلگرام (Photo)** — سریع؛ تلگرام آن را فشرده می‌کند (JPEG).
2. **فایل (Document)** با پسوند **PNG، JPG/JPEG یا WebP** — بایت‌های
   اصلی حفظ می‌شوند؛ برای لوگوی با پس‌زمینه شفاف (PNG) این روش را
   انتخاب کنید. نوع واقعی فایل با magic bytes بررسی می‌شود.

## گزارش فعالیت (بخش‌ها و نگهداری)

بخش‌های گزارش: محصولات و محتوا، سفارش‌ها، **کاربران**، **امنیت و مدیران**،
**سیستم و تنظیمات**. تنظیم `log_retention_days` (پیش‌فرض **۲۰ روز**،
مجاز ۱ تا ۳۶۵) مدت نگهداری رویدادها را تعیین می‌کند؛ پاک‌سازی خودکار
در کرون ۱۵ دقیقه‌ای انجام می‌شود.

## فضای D1 (پاک‌سازی خودکار)

هر ۱۵ دقیقه این داده‌های زائد حذف می‌شوند تا دیتابیس کوچک بماند:
جلسه‌های منقضی ربات، rate-limit های گذشته، رویدادهای تلگرام پردازش‌شده
(۷ روز)، OTP های منقضی، نوتیفیکیشن‌های قدیمی، پنل‌های قدیمی (۳۰ روز)
و درگاه‌پرداخت‌های failed (۹۰ روز). D1 دستور VACUUM ندارد ولی صفحه‌های
خالی‌شده به‌صورت خودکار توسط SQLite دوباره استفاده می‌شوند.

## اعلان‌ها بر اساس دسترسی

اعلان «سفارش جدید»، یادآوری سفارش، تایید پرداخت و رسید جدید فقط به
مدیرانی می‌رسد که کلید **orders** دارند؛ هشدار موجودی فقط برای دارندگان
کلید **products**. سایر پیام‌ها (مثل گزارش) مستقیماً به صاحبان همان بخش
ارسال می‌شود.

## تایید خودکار رسید پس از ارسال

با علامت‌گذاری سفارش به‌عنوان **ارسال‌شده**، اگر رسید کارت‌به‌کارت آن
هنوز «در انتظار بررسی» بود، به‌صورت خودکار تایید و پرداخت‌شده ثبت
می‌شود (رویداد `receipt_auto_confirmed` + شمارش فروش).

## پخش بار D1 (تا ۳ binding)

در پنل Cloudflare همان دیتابیس D1 را حداکثر دو بار دیگر با نام‌های
`DB_R1` و `DB_R2` به ورکر bind کنید (بعد از فعال‌کردن Read Replication
در تنظیمات خود D1). خواندنی‌های عمومی ویترین (bootstrap/products/post)
به‌طور خودکار بین رپلیکاها پخش می‌شوند؛ بدون این binding ها همه‌چیز روی
`DB` اصلی کار می‌کند. پاسخ‌های عمومی به‌مدت ~۳۰ ثانیه در کش لبه هم ذخیره
می‌شوند؛ تغییرات پنل حداکثر پس از ۳۰ ثانیه در سایت دیده می‌شود.

## سرویس پیامک (کد تایید ورود)

تنظیم `sms_provider` (کاوه‌نگار / فراز اس‌ام‌اس / SMS.ir) + `sms_api_key` + `sms_template`
از پنل ربات (🎨 تنظیمات) یا کارت «پیامک کد تایید» مینی‌اپ:

- کاوه‌نگار و فراز اس‌ام‌اس: نام قالب Verify (متغیر `%token`)، مثل `shop-verify`
- SMS.ir: شناسه عددی قالب (TemplateId) با پارامتر `CODE`، مثل `1000123`

## دسترسی‌های مدیران (۱۳ کلید)

products، categories، slider، posts، faq، discounts، cards، orders،
gateway، settings، **sms** (تنظیمات پیامک)، **users** (کاربران سایت)، admins
+ گزارش فعالیت (فقط مدیر اصلی) و تغییر نام نمایشی مدیران با ✏️.

نکته: دکمه‌های ✏️ (تغییر نام) و 🗑 (حذف) در فهرست مدیران فقط برای
**مدیر اصلی** (role=owner) ظاهر می‌شوند. اگر مدیر اصلی اشتباه است،
از پنل 🔑 سطح دسترسی همان مدیر، سطح «مدیر اصلی» را برای ردیف درست
برگزیدید (این کار فقط توسط مدیر اصلی فعلی ممکن است).
